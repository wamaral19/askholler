# Holler evidence-backed tagging system PRD

Status: Implementation-ready product specification
Owner: Holler
Last updated: 2026-11-04
Primary audience: Engineering and LLM-backed coding agents

## 1. Executive decision

Holler will not implement a generic table of free-form tags. Holler will extend
its existing versioned research-field architecture into an evidence-backed
coding system with five distinct layers:

1. **Topics** organize the field library for humans.
2. **Research fields** define the question or dimension being captured.
3. **Controlled values** encode the answer using stable, versioned vocabulary.
4. **Applications** assert that a value applies to a specific interview subject
   and link it to exact transcript and recording evidence.
5. **Facts, segments, findings, and metrics** remain separate from research
   tags, but may be combined with them in analysis and reports.

Hierarchy depth is variable and has no semantic meaning. A controlled value may
be assignable at a broad level when the evidence is broad, or at a more specific
level when the evidence supports it. Ancestors are derived at query time and
are never redundantly applied.

The implementation must build on the existing `research_fields`,
`research_field_versions`, `research_field_sets`, `interview_responses`, and
`response_evidence` model. Do not create a parallel legacy-style `tags` system.

## 2. Product context

Holler conducts point-in-time customer interviews for ecommerce brands and
turns them into evidence-backed findings. The product must preserve the
difference between:

- observed commerce behavior, including Shopify attribution;
- what a customer explicitly says;
- analyst interpretation and recommendations;
- computed metrics such as AOV and LTV; and
- saved customer segments or personas.

The first permanent demo scenario is a fictional outdoor-apparel brand called
**Hollow Peak**. Its primary Research Angle is repeat-purchase growth,
attribution, and category expansion. The permanent dataset covers three months,
contains exactly 10,000 synthetic orders, and includes 50 synthetic completed
interviews.

Prospect-specific demos use the same scenario and generator contracts but
replace brand, product, competitor, channel, volume, and finding vocabulary.
They must remain synthetic and isolated from the permanent canonical demo.

## 3. Confirmed product decisions

- Repository Markdown is the implementation source material.
- Reports are generated by humans from reviewed evidence; LLMs do not publish
  or write report conclusions.
- Transcript coding uses an LLM behind a vendor-neutral provider port.
- Initial transcript submission is manual through an internal UI.
- An approved tag application produced by the LLM is accepted by default after
  deterministic validation, but a human can reject or supersede it.
- A new tag definition suggested by the LLM always requires human approval
  before any application of it can become active.
- Timestamped, speaker-labeled transcripts support links to both transcript
  spans and recording timestamps.
- Plain-text transcripts are allowed, but their evidence is transcript-only.
- The primary customer deliverable is an interactive, private research
  workspace. Every tag, count, customer, and evidence reference is navigable.
- PDF is an optional snapshot/export, not the canonical report or default
  delivery mechanism.
- Merchant authentication is out of scope for the first delivery flow.
  Workspace invitations are sent by email using unguessable, revocable share
  links.

## 4. Goals

### 4.1 Research coding

- Represent structured, comparable research dimensions across merchants.
- Allow merchant-specific extensions without redefining platform semantics.
- Support variable-depth controlled vocabularies.
- Attach every transcript-derived application to exact evidence.
- Preserve model, prompt, definition, field-set, and taxonomy versions.
- Make LLM output deterministic to validate and safe to reverse.
- Support order-, item-, product-, category-, brand-, campaign-, competitor-,
  touchpoint-, and customer-scoped assertions.

### 4.2 Analysis

- Filter interviews by field/value, subject, merchant, Research Angle, period,
  cohort, product, and observed attribution.
- Roll up child values to their ancestors without duplicate applications.
- Distinguish missing, not asked, not answered, not applicable, unknown, and a
  substantive negative answer.
- Count unique interviews or customers rather than raw applications in report
  percentages.
- Preserve separate denominators for commerce populations and interview
  samples.

### 4.3 Reporting and demo

- Render a permanent, believable synthetic research workspace for Hollow Peak,
  a fictional outdoor-apparel merchant.
- Support a dashboard that drills from aggregate counts and clickable tags to
  every matching finding, pattern, interview, transcript span, and recording
  timestamp.
- Generate prospect-specific synthetic datasets from safe configuration.
- Render the interactive workspace from an immutable report revision; support
  optional PDF/print export from that same revision.
- Make every customer-facing claim traceable to authorized evidence or a
  separately identified commerce metric.

## 5. Non-goals

- Automatic report writing or publishing.
- Autonomous creation of production tag definitions.
- Causal marketing attribution claims.
- A merchant-authenticated self-service BI product in the first release.
- Real customer data in demo generation.
- AI-generated interview questions during a live call.
- Replacing human researchers with an AI interviewer.
- A general knowledge graph or arbitrary many-parent ontology.
- Retrofitting raw transcripts into operational logs or job payloads.

## 6. Terminology

| Term           | Definition                                                                       |
| -------------- | -------------------------------------------------------------------------------- |
| Topic          | Navigational grouping for research fields. Topics are not applied to interviews. |
| Research field | Stable semantic identity such as `discovery_source`.                             |
| Field version  | Immutable prompt, value type, scope, evidence, and completion rules.             |
| Value set      | Stable controlled vocabulary used by one or more fields.                         |
| Value option   | Versioned answer such as `word_of_mouth` or `shipping_cost`.                     |
| Application    | A field/value assertion applied to an interview with provenance and evidence.    |
| Subject        | The entity the application describes, such as a product or competitor.           |
| Evidence span  | Exact transcript segment and character range, optionally with recording time.    |
| Coverage       | Whether the field was applicable, asked, answered, skipped, or not applicable.   |
| Commerce fact  | Observed order/customer/product value such as first-order status or AOV.         |
| Segment        | Saved predicate over commerce facts and accepted research applications.          |
| Finding        | Human-authored interpretation that cites evidence and may cite metrics.          |
| Research Angle | Customer segment plus hypothesis/questions; implemented as `ResearchMoment`.     |

The existing `Angle` database entity remains the legacy name for a report
finding. Do not conflate it with a Research Angle.

## 7. Architectural principles

### 7.1 Fields and values, not flat labels

`Meta`, `Google`, `creator`, `UGC`, and `referral` cannot be peers in a generic
tag list. They describe different facets:

- Meta or Instagram is a platform.
- Creator is a discovery or influence mechanism.
- UGC is a creative format.
- Referral may be a discovery mechanism or an advocacy behavior.
- Google may be discovery, influence, trigger, or branded navigation.

The meaning comes from the field, value, subject, and evidence together.

### 7.2 Hierarchy is for vocabulary, not business objects

Value options may form a variable-depth adjacency tree. Each option has one
primary parent. Cross-cutting meaning is represented through separate fields or
facets, not multiple parents.

Rules:

- Group-only options have `assignable = false`.
- Assign the most specific option supported by evidence.
- An assignable parent may be used when the customer was nonspecific.
- Selecting a child does not create stored parent applications.
- Filters may include descendants through a recursive query or materialized
  path projection.
- Renaming changes the label, not the stable key.
- Removing an option means deprecation, never historical deletion.

### 7.3 Customer statements remain separate from observations

An interviewer paraphrase must not be coded as a customer statement unless the
customer confirms it. Researcher observations remain in
`interview_observations` and are labeled `researcher_observed`.

### 7.4 Metrics and personas are not tags

- AOV, LTV, checkout conversion, and repeat rate are computed metrics.
- First-time and repeat-purchaser status are Shopify-derived facts.
- Gifting is captured as `purchase_recipient = gift`.
- Personas are saved segments combining facts and applications.

### 7.5 Every accepted model application is reversible

LLM output cannot update an existing accepted application in place. A human
override creates a rejected or superseding revision and retains the original
provenance.

Retain `interview_responses` as the response/revision envelope. Add:

#### `interview_response_values`

| Column        | Type             | Notes                               |
| ------------- | ---------------- | ----------------------------------- |
| `id`          | uuid PK          | Evidence-addressable assertion atom |
| `merchant_id` | uuid FK          | Tenant guard                        |
| `response_id` | uuid FK          | Parent response revision            |

### 8.6 Response subjects

#### `interview_response_subjects`

| Column              | Type          | Notes                                  |
| ------------------- | ------------- | -------------------------------------- |
| `response_value_id` | uuid FK       | Assertion atom                         |
| `merchant_id`       | uuid FK       | Tenant guard                           |
| `subject_type`      | text          | Field scope enum                       |

| `label_snapshot`    | text          | Historical display meaning             |

### 8.7 Per-value evidence

Add `response_value_evidence` rather than weakening the existing legacy table.

| Column                    | Type             | Notes                                      |
| ------------------------- | ---------------- | ------------------------------------------ |
| `response_value_id`       | uuid FK          | Exact assertion value                      |
| `transcript_segment_id`   | uuid FK          | Exact source segment                       |
| `merchant_id`             | uuid FK          | Tenant guard                               |
| `start_char` / `end_char` | integer          | Exact UTF-16-safe range contract           |
| `start_ms` / `end_ms`     | integer nullable | Recording offsets copied from segment/span |
| `excerpt_snapshot`        | text nullable    | Reviewed/redacted publication snapshot     |

Primary key `(response_value_id, transcript_segment_id, start_char)`.

Acceptance requires at least one valid evidence row when
`evidenceExpected = true`. Evidence must be customer speech unless the field
explicitly permits researcher observation provenance.

This relation is the source of truth for tag placement. A response value may
have multiple evidence spans, and multiple response values may overlap the same
transcript text. Every span belongs to one exact application/value revision;
tags do not belong to prompts, questions, or a completed-call checklist.

### 8.8 Coverage

Extend or replace the reporting projection of `interview_prompt_progress` with
an immutable coverage record after interview completion:

```ts
type FieldCoverage =
  | "not_applicable"
  | "applicable_not_asked"
  | "asked_not_answered"
  | "answered"
  | "declined"
  | "unknown";
```

Store coverage by interview and exact field version. Denominators must be
computed from explicit coverage states rather than inferred from missing tags.

Coverage is a fieldwork-quality signal only. It may answer whether a topic was
asked or answered, but it must never create, own, or imply a tag application.
Prompt progress may remain available while an interview is being conducted;
the completed-call review reads transcript-anchored applications instead.
explicit about whether they use all completed interviews, applicable
interviews, asked interviews, or answered interviews.

### 8.9 Tag-definition proposals

#### `research_field_proposals`

Stores an LLM-suggested field/value concept that is not in the approved
catalog. It is not an active tag definition.

Required fields: `id`, `merchant_id`, `tagging_run_id`, suggested field key,
label, topic, value type, proposed values, explanation, evidence references,
status (`pending`, `approved`, `rejected`, `merged`), reviewer, review time,
and optional resulting field/value IDs.

LLM output cannot directly publish a field, value set, or value option.

## 9. Provenance and review policy

### 9.1 Allowed application provenance

- `human_live`
- `human_reviewed`
- `ai_applied`
- `imported`

`ai_applied` requires model provider identifier, model identifier, provider
request ID when available, prompt-template version, output-schema version,
catalog checksum, transcript checksum, tagging run ID, and acceptance-policy
version.

### 9.2 Default acceptance

An LLM application of an existing approved definition becomes `accepted` only
after all deterministic validators pass. Record:

- `review_status = accepted`
- `accepted_by_policy = true`
- `reviewed_by = null`
- `acceptance_policy_version`

The UI labels it **AI applied - not manually reviewed**. Human confirmation may
set `reviewed_by` and `reviewed_at` without changing the assertion meaning.

### 9.3 Override

- Reject creates a terminal rejected revision; do not delete the row.
- Correct creates a superseding response/application and links the previous ID.
- The previous application no longer contributes to current aggregates.
- Published report revisions remain immutable and retain the applications they
  cited at publication time.
- A later correction creates a new finding/report revision if required.

### 9.4 New definitions

Unknown concepts create pending proposals. Proposed applications are retained
as blocked suggestions and do not contribute to aggregates. Approval publishes
a new field/value-set version and allows an analyst to promote the blocked
applications through a deterministic replay.

## 12. Service boundaries

Add a tagging service to the evidence package. UI and provider adapters must not
write responses/evidence directly.

```ts
interface TaggingService {
  importTranscript(input: TranscriptImportInput): Promise<TranscriptImport>;
  startTaggingRun(input: StartTaggingRunInput): Promise<TaggingRun>;
  getTaggingRun(id: string): Promise<TaggingRunDetail>;
  listCurrentApplications(interviewId: string): Promise<TagApplication[]>;
  rejectApplication(input: RejectApplicationInput): Promise<TagApplication>;
  supersedeApplication(
    input: SupersedeApplicationInput,
  ): Promise<TagApplication>;
  reviewDefinitionProposal(input: ReviewProposalInput): Promise<ProposalResult>;
}
```

Provider port:

```ts
interface TranscriptTaggingProvider {
  tagTranscript(input: ProviderTaggingInput): Promise<ProviderTaggingOutput>;
}
```

The provider receives only the minimum approved transcript segments, field-set
catalog, subject catalog, and output schema. It never receives phone, email,
customer name, raw order payload, or secrets.

## 13. Manual transcript workflow

1. Analyst opens **Evidence > Import transcript**.
2. Analyst selects merchant, existing interview, and pinned Research Angle.
3. Analyst pastes text or uploads `.txt`, `.vtt`, `.srt`, or supported JSON.
4. Analyst confirms speaker mapping and language.
5. System previews normalized segments and timestamp availability.
6. System stores the immutable source checksum and normalized transcript.
7. Analyst chooses **Process tags**.
8. Service snapshots the approved field set and allowed subjects.
9. Provider returns schema-constrained candidate applications.
10. Server validates field/value IDs, exact excerpts, offsets, speakers,
    subjects, tenant ownership, and definition versions.
11. Valid known applications become policy-accepted `ai_applied` responses.
12. Unknown concepts become pending field proposals and blocked applications.
13. Analyst sees a summary and may review, reject, or correct any application.

The full provider contract, validation rules, and operational rollout are in
`docs/transcript-tagging-plan.md`.

## 14. Analyst UI requirements

### 14.1 Field library

- Topic tree on the left; searchable field list on the right.
- Platform and merchant ownership badges.
- Current published version, value type, scope, evidence policy, and usage.
- Enable/disable/default-order controls per merchant.
- Creating or editing publishes a new version; historical versions remain
  inspectable.
- Value trees support group-only and assignable nodes.

### 14.2 Transcript import

- Merchant, interview, Research Angle, language, and source controls.
- Paste and upload modes.
- Segment preview with speaker and timestamp editing before submission.
- Explicit warning when recording links will be unavailable.
- Idempotent duplicate-checksum detection.

### 14.3 Tagging review

- Transcript and recording player remain synchronized when timestamps exist.
- Accepted tags render at their exact transcript spans rather than under the
  research prompt that elicited the conversation.
- Each application displays field, value, subject, evidence excerpt, time,
  provenance, and definition version.
- Clicking an application seeks to the evidence.
- Filters: accepted, manually reviewed, overridden, proposal-blocked, and
  validation failed.
- Actions: confirm, reject, correct, change subject, and propose/merge field.
- Bulk confirmation is allowed; bulk semantic correction is not.

### 14.4 Dashboard

Filters:

- merchant and period;
- Research Angle and cohort;
- first/repeat order fact;
- product, SKU, and product category;
- observed attribution;
- research topic, field, and value;
- application provenance and human-review state;
- transcript timestamp availability.

Views:

- research volume: interviews, minutes, answered fields, accepted applications;
- field/value distribution with explicit denominator;
- observed-versus-stated attribution comparison;
- product/brand/competitor themes;
- saved segments/personas;
- trend by week or month;
- drilldown to interviews and evidence;
- report-finding builder selection tray.

All dashboard counts default to unique interviews. A control may switch to
unique customers or assertion counts, and the active unit must always be
visible.

## 15. Finding and report workflow

1. Analyst filters dashboard evidence.
2. Analyst creates or edits a finding (`Angle` in the current schema).
3. Finding records question, claim, cohort snapshot, period, action, caveat,
   selected evidence, and selected metrics.
4. Percentages require numerator, denominator, population, cohort, period, and
   calculation version.
5. Analyst publishes an immutable finding revision.
6. Analyst assembles a report revision from published findings.
7. The interactive workspace renders from that revision and template version.
8. Tags in findings filter the conversation index directly. The inline tag
   explorer is ordered by current accepted-application frequency, descending.
9. Counts, customers, and transcript/recording references drill into their
   exact supporting evidence.
10. Rendered evidence links use report-share links, not workforce routes.
11. Delivery email links to the workspace. PDF/print is an optional export.

### 15.1 Share links

Until merchant login exists, create opaque workspace-share grants:

- random, unguessable token stored only as a hash;
- scope to one report revision or one authorized evidence item;
- expiry, revocation, and access audit;
- no customer direct identifiers;
- optional merchant email/domain allowlist later;
- recording links generated on demand with a short lifetime;
- transcript page shows only explicitly authorized excerpts or the authorized
  transcript, according to the grant.

Workspace and optional PDF-export links target stable share routes. Neither may
embed signed object-storage URLs.

## 19. LLM safety and validation requirements

- Treat transcript text as untrusted data, never as instructions.
- Use schema-constrained JSON output.
- Pass allowed IDs and keys; do not ask the model to invent database IDs.
- Validate that excerpts exactly match normalized transcript text.
- Validate character offsets and timestamp containment.
- Reject evidence that points only to researcher speech unless permitted.
- Reject values not present in the pinned value-set version.
- Reject subjects not present in the provided subject catalog.
- Do not store chain-of-thought. A short user-facing evidence explanation is
  permitted but is not publication evidence.
- Do not put transcript text, excerpts, or response values in logs, traces, job
  payload summaries, or exception messages.
- Store provider request identifiers and usage totals without prompt/response
  bodies in operational telemetry.

## 20. Security, privacy, and tenancy

- Every new row carrying merchant data includes `merchant_id`.
- Service methods require explicit tenant and actor context.
- Transcript imports and provider payloads are sensitive research data.
- Provider use remains disabled for production transcripts until vendor,
  retention, regional processing, and data-processing terms are approved.
- Demo data must be provably synthetic.
- Report artifacts never include phone, email, customer name, or raw order
  payloads.
- Share-link access is audited without logging the token.
- Deletion/redaction must invalidate or mark unsupported every affected current
  application and finding.

## 21. Observability and failure handling

Tagging lifecycle:

```text
draft_import -> normalized -> queued -> processing
-> validating -> applied | partially_applied | failed
```

- Use the existing transactional outbox and Graphile Worker.
- Idempotency key includes transcript checksum, field-set version, provider
  configuration version, and prompt-template version.
- Provider retry must not duplicate responses or evidence.
- Validation may partially apply valid assertions while quarantining invalid
  assertions, but the run summary must make this explicit.
- Terminal errors expose safe codes, never transcript text.
- A reprocess action creates a new tagging run and may supersede current
  applications according to an explicit comparison workflow.

## 22. Migration strategy

1. Add topics and value-set tables without changing V1 reads.
2. Add V2 definition schema and publish platform value sets.
3. Add normalized response values, subjects, and per-value evidence.
4. Backfill V1 select responses into normalized values when unambiguous.
5. Keep legacy aggregate response JSON until all readers migrate.
6. Add tagging runs/import/proposal tables and provider port.
7. Add analyst UI and dashboard projections.
8. Add workspace-share grants, tag explorer, conversation index, and optional
   PDF/print export.
9. Extend canonical and prospect-specific demo generators.

No migration may reinterpret historical response meaning without preserving the
pinned V1 definition and original value.

## 24. Acceptance criteria

The feature is complete when:

1. An analyst can manually import a timestamped transcript for an existing
   synthetic interview.
2. A vendor-neutral fake tagging provider returns deterministic structured
   applications.
3. Valid applications of approved fields are accepted automatically and show
   their LLM provenance.
4. A human can reject or correct an application without deleting history.
5. An unknown concept enters a human definition-review queue and contributes
   to no aggregate until approved.
6. Every accepted evidence-bearing value opens the exact transcript span and,
   when timestamped, seeks the recording.
7. The dashboard filters and aggregates by field/value with explicit units and
   denominators.
8. An analyst can assemble a human-authored finding from selected evidence and
   commerce metrics.
9. Hollow Peak renders one permanent interactive workspace from a fixed
   three-month, 10,000-order, 50-interview dataset.
10. Every tag, aggregate count, customer reference, and evidence link is
    navigable; optional exports contain no direct customer identifiers.
11. The sample overview contains exactly 50 duration-scaled conversation
    bubbles with accessible hover/focus details, and index rows expose the
    completed-call link plus expandable order detail without quotes.
